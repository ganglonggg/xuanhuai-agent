# 0.6.1：真实合作记录驱动的自主改进

## 直接试用

打开 `dist/宣怀 Agent-darwin-arm64/宣怀 Agent.app`，连接自己的模型后输入创业目标，或选择“创业目标与合作预检”。明确的“我想做/开发……”目标也会从普通对话转入目标工作流。该流程检索历史案例与当前可见项目，不推荐课程。

在“项目与合作”发布真实需求、表达真实意向。双方各自核对并确认授权的技能、每周时数及参与方式后，系统生成结构化预检。本人仍分别决定是否继续以及是否交换联系方式。无需额外点击“学习”或告诉系统应该怎样修改规则。

“项目与合作”新增“合作流程·自主改进”区，显示有效项目数、候选、后续验证进度、真实漏检/误阻断数量以及是否启用。不要为了凑数量创建假项目。没有足够真实记录时，候选保持等待状态。

网页双机版复用相同逻辑；已有后台进程需要重新启动才加载新代码。账号和数据保留，内存中的模型 Key 需重新连接。本轮没有强制退出正在使用的客户端或重启原试用服务。

## 系统自动做什么

1. 只接收实际完成双方授权的合作预检，不从聊天措辞猜测用户失败或训练标签。
2. 从较早的两个不同项目中，发现时间或参与方式的明确冲突，自动生成“在行动规划前检查相应条件”的候选流程。候选空间由程序限定，具体检查哪些维度来自记录。首次接入的历史项目不会被同时用作候选的后续验证。
3. 冻结候选生成时已知的项目，等待之后至少两个不同项目的预检。其中须同时包含有明确冲突和无明确冲突的记录；修改、重试同一项目不算新样本。
4. 将当前流程和候选流程回放到后续记录，比较明确冲突是否被提前识别，以及无冲突项目是否被错误阻断。漏检必须减少，误阻断不能增加，才自动启用。未达到门槛时保留原流程。
5. 下一次创业任务会读取已启用版本，在生成行动计划前检查本人可见且双方授权的预检。已知冲突转为先解决条件；缺乏授权条件则先询问，不作为已核对可直接推进的对象。每份任务报告保存当时的策略版本和检查结果，方便真实比较前后任务。
6. 数据被修改、授权被撤销、需求关闭或可见范围变化，使采用依据不完整时自动回到基础流程。本人也能“暂停改进并恢复基础流程”。不自动发送意向、交换联系方式或发布需求。

## 能力范围

这是有边界的、事件驱动的流程调整：自动触发、从记录归纳检查维度、冻结候选、等待后续证据、验证、应用和依据失效时回退。不调用模型生成任意新代码，不训练模型参数，也不是自由生成新算法。

“冲突”是本人确认的结构化条件之间存在矛盾，不等于现实合作失败。“漏检减少”衡量流程对这类条件的处理，不代表创业成功率、匹配质量或合作成功率提升。无明确冲突也不表示技能和其他条件全部满足。当前只调整时间和参与方式的检查顺序。

目前代理协作仍是固定三轮授权卡协议；目标报告的双模型上下文属于辅助分析，不是两个远程身份的自由多轮谈判。真实云端模型质量、延迟及真实用户效果仍要在试用中观察，不能将隔离测试结果作为已经发生的用户改进。

## 工程验证

新增测试覆盖：确认事件自动触发、候选与后续记录隔离、同项目去重、同时需要正负记录、第三方隔离、依据撤销回退、暂停、持久化，以及晋级后下一次创业任务实际改变处理顺序。所有测试使用隔离数据，不向试用账号注入记录。

信息服务与桌面测试命令：

```
npm --prefix 信息层/xuanhuai-platform test
npm --prefix 客户端 test
```

界面验证使用隔离模型响应；运行 `客户端/scripts/verify-ui.js` 与 `客户端/scripts/verify-venture-ui.js`。正式运行仍使用用户配置的模型。
